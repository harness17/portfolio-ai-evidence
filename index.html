担当した課題と、そのときの判断

パフォーマンス改善

表示処理の遅延を、データアクセス設計の見直しで解消

課題
複数のデータを連結して表示する画面で、DBアクセスがレコード単位に個別発行されており、表示までに大きな遅延が発生していた。
判断
表示時の逐次取得をやめ、必要な関連データを先にまとめて取得してからメモリ上で突き合わせる方式へ変更。一括取得できるものは可能な限り結合し、アクセス回数そのものを削減した。
結果
画面表示の遅延を解消。以降は同種の画面でも先行取得を前提とした実装方針を取るようにした。

開発標準の策定 · リーダー

社内の開発標準を策定し、実装方針をサンプルとして展開

課題
実装方針が担当者ごとに揺れると、レビューと保守のコストが上がる。
判断
設計方針を主体となって策定し、基本的な実装方針を組み込んだサンプルページを自ら作成して開発標準として展開した。
結果
社内の開発標準として運用。この取り組みを現在の技術で作り直しているのが DevNext。

要件定義 · 顧客折衝

実現困難な要求を、代案提示で合意可能な仕様に落とす

課題
利用者が使う検索画面の挙動について、顧客の要求をそのまま実装すると動作として無理が出る内容だった。
判断
要求の意図を汲んだうえで、開発上・操作上とも不自然にならない挙動を代案として提示した。
結果
顧客と合意して仕様を確定。営業・SEが持ち帰った情報をもとに、要求整理・要件定義から実装設計までを担当した。

品質 · 運用改善

入力ミス起因の確認作業を、バリデーションと事前検証で削減

課題
旅行予約システムでプラン変更や細かな設定確認が繰り返し発生し、入力ミスに起因する確認作業が残っていた。
判断
入力段階のバリデーションを追加し、あわせて異常系が発生しないためのデータ検証を後から組み込んだ。
結果
入力ミスの発生と、それに伴う確認・対応の手間を削減した。

How I work

開発の進め方

AIを使って開発を効率化する一方で、設計・守秘・公開可否の判断は自分で行います。Claude CodeとCodexの連携を仕組み化し、品質を落とさず手戻りを減らしています。

自分で決めること

  • アーキテクチャと設計判断
  • 守秘・個人情報・公開可否の判断
  • 完成条件と検証観点の定義

仕組み化していること

  • AI間のhandoffを多層契約（目的/範囲/権限/完成/検証/失敗）で定義
  • 変更差分を絞るSurgical Changesルール
  • レビューゲートと、手順のskill化による再利用

検証のしかた

  • dotnet test / npm test
  • Playwrightによる実動確認
  • Claude Code↔Codexのクロスレビュー
