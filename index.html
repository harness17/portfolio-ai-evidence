社内改善 · ツール導入

散らばっていた部内の案件管理を、Redmineの導入で見える化

課題
部署内の案件管理をメールやSkypeで行っていたため、各人のタスクや問い合わせが散らばって判断が難しくなり、誰が何を担当しているかも把握できていなかった。
判断
無料で社内に置け、広く使われているRedmineを選んで導入を提案。余っていたPCで社内サーバーを立ち上げ、インストール・設定・ユーザー管理から、プロジェクトとタスクの管理方法、チケットの切り方のルール決めと部内への説明まで一人で行った。
結果
プロジェクト単位でタスクを管理できるようになり、部署内で何が動いているか、業務の大枠が見えるようになった。各人のタスク量も把握できるようになり、部内の連絡が滞らなくなった。個人でも自分の受け持ちやタスクの受け渡しが分かるようになり、仕事が進めやすくなった。退職まで運用を担当した。

パフォーマンス改善

申込一覧の表示の遅れを、データの取り方の見直しで解消

課題
旅行予約システムの申込一覧画面に申込内容を表示する列があり、その対象プランを施設ごとに1件ずつ取得していた。DBアクセスがレコード単位に発行され、表示までに大きな遅延が出ていた。
判断
データは「申込 → 施設 → プランごとの申込情報 → プラン」と階層でつながっていた。この階層を施設ごとにたどって取得するのをやめ、メモリ上で申込と突き合わせる方式へ変更。一括取得できるものは可能な限り結合し、アクセス回数そのものを減らした。
結果
画面表示の遅延を解消。以降は同種の画面でも先行取得を前提とした実装方針を取るようにした。

開発標準の策定 · リーダー

共通ライブラリとひな形を整え、社内の新規開発案件4件の標準に

課題
社内のWebシステム開発で、実装の仕方が担当者ごとにそろっていなかった。実装方針が揺れると、レビューと保守のコストが上がる。
判断
旅行予約システムの実装から汎用的な部品を抜き出して土台にした。エンティティとリポジトリの基底クラスでDBまわりとCRUDを共通化し、PDF・Excel出力、ファイル取込、バッチ処理のサンプルを用意。管理画面はBootstrapベースでデザインを統一し、ページャーなどの部品も共通化した。以後は案件で必要になった機能を切り出して取り込んだ。
結果
演題処理システムを含む社内の新規開発案件4件で、標準として使われた。開発は当初から実質的に担当し、2020年9月からは取りまとめも引き継いだ。この共通基盤を ASP.NET Core 10 の構成に移し替えたのが DevNext。

要件定義 · 顧客折衝

地域の選択肢に別の条件を混ぜる要求を、代案で合意できる仕様に落とす

課題
旅行予約システムの利用者側の検索画面で、地域を選ぶセレクトボックスの中に、別の項目としてチェックで絞り込んでいた条件を入れるよう指示が出ていた。そのまま実装すると、性質の違う条件が地域と同じ選択肢に並び、地域とその条件を同時に指定できなくなる。
判断
地域とは別口で設定しなければならない条件だと説明し、これまでどおりチェックボックスで指定する形を代案として出して折衝した。
結果
顧客と合意して仕様を確定。営業・SEが持ち帰った情報をもとに、要求整理・要件定義から実装設計までを担当した。

品質 · 運用改善

「プランが表示されない」問い合わせを、設定時の整合性チェックでなくす

課題
旅行予約システムで、管理者が宿泊プランを設定するときに販売期間と公開期間の組み合わせを間違えることがあり、運用担当者から「プランが表示されない」「申し込みができない」という問い合わせが定期的に来ていた。
判断
誤った設定が保存されないよう、入力の段階で矛盾を止める方針にした。保存時に販売期間が公開期間からはみ出していればエラーにし、あわせて施設情報とプラン情報が矛盾しないかのチェックも組み込んだ。
結果
設定ミスによる問い合わせが、ほぼ来なくなった。

設計 · 共通化

学会ごとに違う設問を、開発なしで設定できるフォーム設計に

課題
演題処理システムで、旅行予約システムにあるような自由設問を3つのフォームに入れる要望が出た。旅行予約版はフォームの型が決まっておらず、設問を出すにはHTMLと表示用のタグを書く必要があったため運用側では扱えず、細かなカスタマイズや修正・新規登録のたびに開発へ手戻りが出ていた。
判断
使い回さず、3フォームの仕様を共通化して設計し直した。テーブルは「フォーム → 基本／自由設問 → 選択肢などの小項目」、回答は「基本回答 → 自由設問の回答」とし、回答に設問と小項目を結合すれば入力時の項目を再現できる形にした。「ラジオで2を選んだときだけ表示する」といった連動設問は、表示制御を汎用のJS関数にまとめて動的に切り替えた。
結果
学会ごとの設問の違いを、開発なしで管理画面から設定できるようになった。3つのフォームを同じ仕組みで保守でき、表示制御も汎用関数にまとめたことで、メンテナンスの手間を大きく減らせた。

Chrome · Firefox extension · MV3

YouTube Playlist Date Sorter

課題
YouTubeのプレイリストを投稿日順・タイトル順・再生時間順に並べ替えて見たい。APIキー不要で動かしたい。
役割
企画・実装・ストア公開まで一人で担当。
使用技術
Chrome Extensions (MV3) / JavaScript / DOM / MutationObserver
判断
利用者にAPIキーを用意させない方針を要件に置き、ページのDOMだけで完結させた。YouTubeは再描画のたびに行の順序を戻すため、DOMは動かさずCSSのorderで表示順を固定。MutationObserverはプレイリストの行構造の変化だけを監視し、サムネイルの読み込みなどで並び替えが繰り返し走らないようにした。
成果
Chrome Web Store · Firefox Add-ons 公開（v0.2.0）。投稿日順・タイトル順・再生時間順ソート＋連続再生をAPIキー不要で実現。

Chrome · Firefox extension · MV3

Amazon Wishlist Sale Picker

課題
Amazonのほしい物リストから、セール対象の商品だけを抽出して見たい。
役割
企画・実装・ストア公開まで一人で担当。日英UIに対応。
使用技術
Chrome Extensions (MV3) / JavaScript / DOM / MutationObserver
判断
ほしい物リストはスクロールで後から読み込まれるため、自動スクロールで全件を読み込んでから判定する方式にした。待機は固定時間ではなく MutationObserver で商品の追加を検知して進め、終了はAmazon側の終端マーカーで判定する。スクロール回数で止めていた頃は長いリストで368件中290件しか対象にならなかったため、終了条件をページの状態に切り替えて取りこぼしを防いだ。
成果
Chrome Web Store · Firefox Add-ons 公開。複数のリストを横断してセールを確認する機能も実装。日本語・英語の両UIに対応。
Chrome Web Store Firefox Add-ons GitHub

How I work

開発の進め方

AIを使って開発を効率化する一方で、設計・守秘・公開可否の判断は自分で行います。Claude CodeとCodexの連携を仕組み化し、品質を落とさず手戻りを減らしています。

自分で決めること

  • アーキテクチャと設計判断
  • 守秘・個人情報・公開可否の判断

仕組み化していること

  • AI間のhandoffを多層契約（目的/範囲/権限/完成/検証/失敗）で定義

  • レビューゲートと、手順のskill化による再利用

検証のしかた

  • dotnet test / npm test
  • Playwrightによる実動確認
  • Claude Code↔Codexのクロスレビュー
